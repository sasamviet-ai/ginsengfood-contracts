# Changelog

Changelog này ghi lại thay đổi của contract repo `ginsengfood-contracts`. Mọi thay đổi ảnh hưởng đến API, event, schema, enum, state machine, error code hoặc compatibility policy cần được ghi tại đây.

## Unreleased

### SKU read model: `updated_at` and `revision` (SKU-M12-03, additive)

Prepared on top of `e60df94` for the business-platform (M3) review. **Classification: additive.** Two optional properties join `schemas/product/sku.schema.json`, the object returned by `getSkuV1` (and by the SKU list route added in the next changes of this series):

- `updated_at` - UTC date-time of the latest change to what the object publishes (the SKU master record; the trade-item packaging configuration joins it with `sellable_uoms`). Never null: a SKU that was never edited carries its creation instant. Not moved by a change of the recipe, formula, BOM or activation pointers.
- `revision` - integer, strictly greater after every change counted by `updated_at`. Compare only against an earlier value of the same `sku_id`; not a counter, no gap-free guarantee. The provider derives it from the change instant today and may move to a stored counter later without a contract change.

Neither is in `required`, so a consumer that validates a response of an older provider keeps working; an ops-core build that carries SKU-M12-03 always emits both. Example `examples/api/x03b/sku.response.json`, fixture `contract-tests/x03b/fixtures/sku.response.fixture.json`, and `contract-tests/x03b/sku-catalog-v1.contract.test.mjs` (wired into CI, with its own small schema validator in `contract-tests/x03b/lib/mini-schema.mjs`) pin the shape and eight tamper cases. The `getSkuV1` operation block is untouched.

### Reserve: per-principal quota refusals and the hold window (SEC-14)

Additive documentation of behaviour the provider now has; no new `error.code`, the closed enum of `external-allocation-reserve-error.schema.json` is unchanged. `reserveInventoryAllocationV1`: quota refusals are `409 ALLOCATION_CONFLICT` with `error.details[0].reason` of `HOLD_LIMIT_REACHED` (active holds of the principal) or `HOLD_SHARE_LIMIT_REACHED` (share of the SKU on-hand stock), not shortages, nothing is reserved and the same key may be retried after holds are released or expire. Limit validation is `422 VALIDATION_FAILED` with `details[].reason` of `REQUESTED_QUANTITY_LIMIT_EXCEEDED` or `EXPIRES_AT_LIMIT_EXCEEDED`. The maximum `expires_at` window is provider configuration, 60 minutes by default (the 24-hour ceiling is unchanged); omission still means 30 minutes. `listInventoryAllocationsV1`: consumers must always send `sourceObjectId`; a later revision makes it required (`422` reason `SOURCE_OBJECT_ID_REQUIRED`), switched on by a provider flag after this contract is published and the pin has moved.

### Reserve request: source_object_no allows 200 characters (SEC-07b)

`source_object_no` in `external-allocation-reserve-request.schema.json` goes from `maxLength: 100` to `maxLength: 200`, matching what ops-core validates since SEC-07 (longer values answer 422). This only widens what a consumer may send; it is still a display and reconciliation reference, never an identity key.

### Webhook security profile and inventory payload allowlist (SEC-12, SEC-13)

Prepared on top of the pin `a7832a49` for the business-platform (M3) review, next to the allocation write surface below. Source: ops-core plan rows SEC-12 (M12-082) and SEC-13 (M12-083), security review PL-H K5 (gaps GAP-04, GAP-07, GAP-08, GAP-21). **Classification: narrowing, owner decision, coordinated.** By the letter of `compatibility/breaking-change-policy.md` it tightens published event schemas in three ways, and the first counts as breaking: (1) it removes seven optional properties from `stock-below-threshold` and `stockout-risk-detected`; (2) it caps `data.reason` at `maxLength: 200` on `sale-lock-activated`, `stop-sale-required` and `sale-lock-released`; (3) it ties the threshold name of `stock-below-threshold` to the status with an if/then rule (a yellow alert carries `yellow_threshold` and not `red_threshold`, a red alert the opposite; the pinned schema leaves both optional). It is published because there is no consumer to break (M3 has no webhook receiver yet and the provider's webhook is not enabled in production), and under `VERSIONING.md` the M3 owner confirms before merge that M3 reads none of the seven fields below, needs no `reason` text beyond 200 characters, and does not rely on the `yellow_threshold` of a red alert (the old provider behaviour, which carried the red value under the wrong name). Provider code and this contract are independent of each other in the order they can land: the provider's change is valid against both the pinned and the new schemas, so the provider goes first, then this contract, then the pin moves.

#### Provider behavior coming with ops-core SEC-12 / SEC-13 (NOT live yet)

This describes the provider after the ops-core change of 12/11/2026, not the provider running today. Today the three inventory events send their whole internal `data`, including the seven fields above and `null` for empty optional keys; the sale-lock `reason` goes out as typed; there is no body cap; the webhook client follows redirects (a `307` re-sends the signed body to the `Location`); `X-Webhook-Key-Version` carries whatever the deployment configured, from a version variable shared with four other secrets.

- (a) The three inventory events build `data` from an explicit list of keys (`docs/webhook-security.md` section 8); optional keys without a value are absent, never `null`.
- (b) The sale-lock `reason` is normalised and capped at 200 characters as described above.
- (c) A body above 65 536 bytes is not sent and goes to dead-letter.
- (d) The provider's webhook client does not follow redirects (`AllowAutoRedirect` off): a `3xx` is a failed attempt.
- (e) Outside development the provider refuses to start when the key-version label does not match the grammar; the deployment configures the webhook key version on its own variable (it falls back to the version shared with the other four secrets while unset).
- (f) `stock-below-threshold` names the crossed threshold after the status. Today the provider sends the red value under `yellow_threshold` for a `STOCK_RED_ALERT` and never sends `red_threshold`; from this change a red alert carries `red_threshold` and a yellow one `yellow_threshold`, never both. Events already queued in the provider's outbox are corrected when they are sent.

### Allocation write surface: self-release and `ISSUED` (additive, coordinated)

Prepared on top of the pin `a7832a49` for the business-platform (M3) review. **Classification: additive, coordinated.** Under `compatibility/breaking-change-policy.md` a new enum value and a new operation are non-breaking when consumers must already tolerate unknown values, but `ISSUED` is the first value a consumer can actually receive that the 2026-09-21 schemas did not list, and the release command is the second consumer-driven write. The contract cannot hold the provider back: `ISSUED` appears as soon as the warehouse applies a sales issue document. The gate that can actually be checked is on the consumer side: the business-platform does not read allocations in production until its status parser tolerates `ISSUED` and unknown values and the business-platform owner has confirmed that (`VERSIONING.md`: review by provider and consumer owner before merge). Consumers must tolerate unknown `status` values.

#### Added

- **`releaseInventoryAllocationV1`** - `POST /v1/inventory/allocations/release` in `openapi/ops-core/inventory.v1.yaml`. Body `{source_object_type, source_object_id}`; header `X-Idempotency-Key` required. Releases every RESERVED line that the calling service principal created for the source and that has not expired, or releases nothing. Same permission (`INVENTORY_ALLOCATION_CREATE`) and audience (`ginsengfood-ops-core-external-allocation-v1`) as reserve, same `ExternalAllocationWrite` bucket; the warehouse permission `INVENTORY_ALLOCATION_RELEASE` is not granted to consumers. Answers: `200` `RELEASED` with the released lines, `404` when the principal holds nothing for the source (another principal's source looks identical), `409 ALLOCATION_CONFLICT` when the warehouse already CONFIRMED or ISSUED stock of the source (nothing is released), `409 ALLOCATION_NOT_HELD` when everything was already released or expired, `422` for a missing, malformed or over-long key or a key reused for a different source, `403` for a key first used by another principal, `429`. A replay with the same key returns the original 200 body. No ledger entry, no goods movement. Owner decision OD-M3-REPLY-01 (2B, 2026-10-08).
- **`ISSUED` allocation status** - added to `external-inventory-allocation.schema.json` and `external-allocation-reserve-line.schema.json`; the status vocabulary is now one file, `enums/ops/inventory-allocation-status.yaml` (RESERVED, CONFIRMED, ISSUED, RELEASED), and the lifecycle is documented in `state-machines/ops/allocation-state.md` (RESERVED -> CONFIRMED -> ISSUED; RESERVED or CONFIRMED -> RELEASED; expiry ends in RELEASED; CONFIRMED never expires). `ISSUED` adds no field to the projection. Reserving a source whose allocation of the same principal was already issued is `409 ALLOCATION_CONFLICT` whatever the idempotency key (C37, OD-ALLOC-CONSUME-01); an `ISSUED` allocation of another principal is answered `409 INSUFFICIENT_STOCK` (see WP07b (a) below).
- **`ALLOCATION_NOT_HELD`** (409) - exists only in the new closed enum of `schemas/ops/x03b/external-allocation-release-error.schema.json`; recorded in `error-codes/external-allocation-errors.yaml`. New schemas: `external-allocation-release-request`, `-release-result`, `-release-line`, `-release-error`; examples under `examples/api/x03b/` (release request/response, two release errors, an `ISSUED` snapshot).
- **Contract tests and fixtures for the write surface.** Reserve had none. `contract-tests/x03b/external-allocation-write-v1.contract.test.mjs` checks both operations' metadata, every response mapping, all request/result/error payloads (examples and fixtures under `contract-tests/x03b/fixtures/`), the status vocabulary parity and tamper cases, and is wired into CI. `reserveInventoryAllocationV1` and `releaseInventoryAllocationV1` join the X04D security metadata test (26 operations).
- **`docs/webhook-transport.md`** - the HTTP webhook transport that existed only in the M3 handoff package: HMAC-SHA256 over `"{timestamp}\n{eventId}\n" + raw body`, the `X-Outbox-Event-Id`, `X-Webhook-Timestamp`, `X-Webhook-Key-Version` and `X-Webhook-Signature: v1=<hex>` headers, 300 second clock skew, at-least-once delivery, retry and dead-letter rules, and the 13 routed event types. #### Provider behavior coming with ops-core WP07b phase A (NOT live yet)

The text of this change for the points below describes the provider after ops-core WP07b phase A (owner decision of 2026-11-11), not the provider running today. Publish this contract and move the ops-core pin in the same step, and do not code against today's behavior or against the wording of the earlier pin:

- **(a) A hold of another principal is never reported as yours.** A reserve call for a source that is held by another service principal is `409 INSUFFICIENT_STOCK` and the holder is not disclosed, so `INSUFFICIENT_STOCK` has five undisclosed causes, not four. `200 ALREADY_RESERVED` applies only to the calling principal's own hold. This holds for a hold in any state: a source whose allocation was `ISSUED` for another principal is also `409 INSUFFICIENT_STOCK`, not `ALLOCATION_CONFLICT` (that code is kept for an `ISSUED` allocation of the calling principal itself). Today a repeat call can be answered `ALREADY_RESERVED` for another principal's hold.
- **(b) `GET /v1/inventory/allocations` lists only allocations created by the calling principal.** Today it lists all of them. A `CONFIRMED` or `ISSUED` row of another principal is no longer visible.
- **(c) A call whose first attempt with the same `X-Idempotency-Key` is still running is `429` with `Retry-After: 1`, for both reserve and release.** Today release answers `409 ALLOCATION_CONFLICT`, and reserve can answer an in-flight `202` that this contract never described. The `X-RateLimit-*` headers are optional on that `429`, because the endpoint produces it, not the bucket. `ALLOCATION_CONFLICT` on release is therefore left with two causes: the warehouse already confirmed or issued stock, or the allocation changed mid-call.
- **(d) Reserve: the same key reused with a different body for the same source is `422 VALIDATION_FAILED`** with `details[].field` set to `X-Idempotency-Key`, and the body fingerprint now includes `expires_at`, so a retry must resend the original `expires_at` unchanged. Today that case is answered `409 INSUFFICIENT_STOCK`. The reserve idempotency scope is the source: a key sent for a different source is a new command. Release keeps its scope of the key alone, where a key reused for a different source is already `422`. A key first used by another service principal is `403` for both commands, today as well.
- **(e) Temporary contention is `429`, not `409`** (provider commit `d55ff75a0`, local, not pushed). When the SERIALIZABLE transaction of reserve or release is rejected by PostgreSQL and the server has used up its 6 attempts (about 375 ms of sleeping at most), the answer is `429` with `Retry-After: 1`, `error.code = RATE_LIMITED`, `error.httpStatus = 429`, the message "The request could not be completed because of concurrent activity. Retry later with the same X-Idempotency-Key." and no `details`. It is the same code and status as the in-flight same-key case (c); only the message differs. For M3 it is not out of stock and changes no state: the transaction did not commit, so the key is reusable. Wait `Retry-After`, repeat with the same `X-Idempotency-Key` and the same body, up to about 5 times, then treat the outcome as unknown. Until this change the same situation was answered `409 INSUFFICIENT_STOCK` (reserve) or `409 ALLOCATION_CONFLICT` (release), so those two `409` answers now never mean contention. The 429 components of both operations describe the three causes (empty bucket, same key still running, contention); `docs/m3-allocation-integration-notes.md` has the retry guidance. Internal and admin endpoints keep `409 CONCURRENCY_CONFLICT` for the same situation.

#### Changed

- **`ExternalAllocationWrite` is now defined** in `inventory.v1.yaml` `x-rate-limit-policies` (5 per second per principal, burst 10, fleet 25, no queue), as decided under C25 on 2026-09-08. The 2026-09-21 contract referenced it without defining it and still carried a comment saying the route temporarily used the hot bucket; both are fixed. Reserve and release share the bucket. The two 429 answers are now components with a required `Retry-After`; the `X-RateLimit-*` headers are optional, present only when the bucket itself rejected the call.
- **`X-Idempotency-Key` is one definition**: 1 to 200 characters of `[A-Za-z0-9:_.-]`, `components.parameters.IdempotencyKey`, used by reserve and release. Reserve previously said at most 100; the provider has always accepted 200 and enforced the charset (M3 handoff TB-08). The length limit is raised to the provider's 200, and the character set is tightened on paper to what the provider has always enforced, so no key that the old text allowed and the provider accepted is affected; a key with a character outside `[A-Za-z0-9:_.-]` was never accepted at runtime.
- **Reserve `409` description corrected to what the provider returns** (description only, no status or code moved): `INSUFFICIENT_STOCK` covers undisclosed causes - short stock, blocked lots, the same source already holding a different warehouse, unit or quantity, more than 20 lots (and, from ops-core WP07b, a fifth: the source held by another principal) - and `ALLOCATION_CONFLICT` means the hold of the key is no longer held (expired, or released by the warehouse or by consumer self-release) or the source was already `ISSUED`. The earlier text said a different scope returned `ALLOCATION_CONFLICT`.
- **X04D metadata on reserve**: `x-retry-policy: ExternalManualReplayOnly`, `x-idempotency-disposition`, `x-runtime-policy`, `x-owner-decision-ref` and an `x-audience-catalog` in `inventory.v1.yaml`, so both write operations are covered by the same security metadata test as the read operations. Metadata only.
- **`availability-consumer.v1.yaml` request mirror** now equals the provider's closed request (`sku_id`, `warehouse_id`, `batch_id`, `requested_quantity` as `{value, unit}`, `uom_code` in `hộp`, `thùng`, `lọ`, `hũ`, `channel_context`, `correlation`); the invented `channel_context_id` and `customer_id` fields are gone. `examples/api/availability-check.request.json` is the bare provider body with UUID ids and unit `hộp` instead of an enveloped body with unit `pack`. The `200` response of the mirror now points at `schemas/ops/sellable-status.schema.json` like the provider (it pointed at `schemas/commerce/availability-check.schema.json`, a different 14-property shape that matched neither the provider nor the response example), and `429` is declared. The `block_reasons` mapping that the 2026-09-09 entry below says moved into this file is still not in it.
- **Compatibility matrices**: `consumer-compatibility-matrix.md` records the allocation hold and self-release as the one deliberate exception to "business-platform must not mutate inventory truth"; `api-version-matrix.md` points to it.

### Changed

- **Ops-core v1 catalog field parity (2026-09-21):** `sku.product_id` is documented as the same identity as `sku_id` under accepted `OD-A6-01`. The field was already optional in the published schema; the provider now supplies that alias without introducing a separate Product aggregate.
- **Recipe/formula v1 audit boundary (2026-09-21):** `audit_refs` remains optional and is explicitly **NOT emitted** by the ops-core v1 provider under accepted `OD-N10-N13-2026-09-21/D1 = NEVER_EMITTED_V1`. Internal audit/actor data remains outside these projections; omission does not assert that no audit exists. This documents existing response behavior: no field, type, required list, permission, lifecycle, or route changes, and no v2 cutover. Future external audit disclosure needs a separate scope/redaction/data-source/versioning decision.


- **`POST /v1/availability/check` absorbs what v2 could do: it returns numbers.** The request accepts an optional top-level `uom_code` (`hộp`/`thùng`/`lọ`/`hũ`, Ordinal, no conversion). Supplying it makes the response carry eight additional properties - `uom_code`, `warehouse_scope`, `check_mode`, `available_quantity`, `sellable_quantity`, `fulfillable`, `resolved_at`, `valid_until`. Omitting it leaves the response byte-for-byte identical to the pre-merge shape, so the change is purely additive for anyone already reading v1. When both `uom_code` and `requested_quantity.unit` are supplied they must match exactly; a mismatch is `422`, never a silent pick. A `warehouse_id` that does not resolve to an ACTIVE warehouse is `404` and never falls back to `ALL` scope.
- **`block_reasons` keeps the producer vocabulary.** v2's closed 15-value enum required a projection layer over the 11 tokens ops-core actually emits: it renamed `HSD_NOT_VALID` to `HSD_EXPIRED`, split `STOCK_NOT_AVAILABLE` in two, folded `SKU_ACTIVATION_NOT_ACTIVE` into `SKU_NOT_ACTIVE`, and demoted `INVENTORY_LEDGER_NOT_PASSED` - an internal data inconsistency - to `PROVIDER_UNAVAILABLE`, a word that reads like a transport failure. Merging into v1 deleted that layer, so consumers now see the same 11 tokens the domain produces, at full resolution. Four v2-only tokens (`UOM_NOT_ACTIVE`, `UOM_MISMATCH`, `RESOLUTION_TIMEOUT`, `FLEET_AUTHORITY_UNAVAILABLE`) are not carried over: no runtime path ever emitted them, and the conditions they named are HTTP statuses (`422`, `408`, `503`), not business reasons.
- **`decision` stays two-valued.** v2 added `UNKNOWN` because its enum had no token for `INVENTORY_LEDGER_NOT_PASSED` and it had to fail closed on something. v1 has that token, so it reports `NOT_SELLABLE` with the actual reason instead.

### Changed

- **Inventory allocation reserve gets its own rate bucket.** `reserveInventoryAllocationV1` now declares `x-rate-limit-policy: ExternalAllocationWrite` instead of sharing `ExternalAvailabilityCheck` with the availability checks. The provider partitions by policy name and principal, not by route, so all three operations drew from one token bucket with no queue - and the v2 recheck policy requires an availability call at five checkpoints, so checks outnumber reservations several times over. A burst of checks therefore rejected the one operation that prevents overselling. Consumers see no shape change; the reserve call now has its own sustained 5 / burst 10 / fleet 25 allowance that check traffic cannot drain. Owner decision C25 (2026-09-08).
- **X03B stock-alert projection**: `resolved_at` documented as never emitted by v1. The provider models stock alerts as an append-only event stream - each evaluation writes a new row carrying `status`, and no resolved or closed column exists anywhere near it - so the field had nothing behind it. It was already optional, so leaving it empty never violated the schema; what was wrong is that it carried no description, unlike `location_type`, so a consumer reading the contract would wait for a timestamp that never arrives. The information is not lost: `status` already publishes all five values including `STOCK_OK`, so resolution is the most recent event for the same `sku_id` and `warehouse_id` reporting `STOCK_OK`, resolved at that event's `occurred_at`. Description-only change - no field, shape or status code moved. Owner decision `OD-C28-STOCK-ALERT-RESOLVED-01` (2026-09-08).
- **Recipe, formula, BOM and ingredient reads move to their own permission.** `getRecipeV1`, `getFormulaVersionV1`, `getBomV1` and `getIngredientV1` now declare `x-permission: RECIPE_PRODUCTION_VIEW` instead of `SKU_CATALOG_VIEW`. One scope previously covered five operations, so any consumer holding it to read `getSkuV1` could also read the entire approved formula: measured on the ops-core sandbox with the Module 3 development token, `GET /v1/boms/{bomId}` returned 29 BOM lines with `ingredient_id` and quantity, and `GET /v1/ingredients/{ingredientId}` resolved those ids to ingredient codes. `getSkuV1` keeps `SKU_CATALOG_VIEW` and still returns `recipe_id`, `bom_id` and `formula_version_id`, which become undereferenceable pointers for a consumer without the new permission. Audience, auth class, rate policy and every field stay unchanged, so this is a permission narrowing, not a shape change: a consumer that was granted only what it needs is unaffected, while one relying on formula reads through `SKU_CATALOG_VIEW` must request `RECIPE_PRODUCTION_VIEW`. Owner decision `OD-B10-01` (2026-09-08).
- **Recall/sale-lock wire scope identity**: `TRACE_CHAIN` carries `scope_id = recall_case_id` — the complete versioned historical impact union for that case — not the narrower QR, warehouse-receipt, shipment or customer id it previously echoed. Consumers that resolved `scope_id` as one of those narrower objects must re-read it as a recall case id. The behaviour shipped in ops-core `64d503a37` and is described on `createSaleLockV1` in `openapi/ops-core/recall-sale-lock.v1.yaml`, but the description alone never announced that the meaning of an existing field had changed, so nothing told a consumer already reading it to look again. Recorded here for that reason. Affects the sale-lock read path and the `ops-core.recall.sale-lock-*` / `stop-sale-required` events; reviewers on M3, M6 and M8 should confirm they do not dereference `scope_id` as a QR or receipt id.
- **X03B warehouse-location projection**: `location_type` moved out of `required` and documented as never emitted by v1. The provider has no approved taxonomy and no source column for it, so requiring it forced a fabricated value. Consumers must not infer it from `location_code`, `location_name` or warehouse type, and must not read its absence as a defect. Owner decision `OD-C24-02` (2026-09-05).
- **X03B warehouse-receipt projection**: `status` enum reconciled to the canonical ops-core lifecycle `DRAFT|PENDING_CONFIRMATION|CONFIRMED|CANCELLED|CORRECTED`, and `received_quantity` moved out of `required`. The header roll-up is emitted only when every receipt line shares one UOM — summing mixed UOM lines produces a silently wrong number — so absence means "not expressible as a single quantity", never zero. A `CORRECTED` receipt keeps the quantity recorded on the receipt itself — `OpWarehouseReceipt.Correct` only advances the status and never rewrites the receipt lines, so the corrected amount is carried by a separate document; an earlier draft of this entry claimed the opposite and was wrong. Owner decision `OD-C24-03` (2026-09-05).
- **X03B stock-balance projection**: `item_type` narrowed to `FINISHED_GOOD` so the finished-goods-only boundary is structural rather than provider-code-only, and `material_id` documented as reserved and never emitted at this scope. The three hold quantities are now specified as a **disjoint partition** with priority `recall > sale lock > quality hold`, carrying the invariant `on_hand = available + reserved + quality_hold + recall_hold + sale_lock` at every row and aggregation, so consumers may add and subtract them without double counting. A row under several restrictions reports only its highest-priority reason. `POST /v1/availability/check` remains the sole commit authority. Owner decisions `OD-C24-01` and `OD-C24-01B` (2026-09-05).
- OpenAPI validation now derives major from `.vN.yaml` and checks matching `info.version` plus `/vN` paths.
- Documented that `sellable_status_id` returned by `POST /v1/availability/check` is **ephemeral**: that path evaluates without persisting, so the identifier is newly generated per call and `GET /v1/sellable-statuses/{sellableStatusId}` with it always returns `404`. Only identifiers carried by `ops-core.sellable.*` events resolve. Description-only change on `openapi/ops-core/availability-sellable.v1.yaml` and `schemas/ops/sellable-status.schema.json` — no field, shape or status code changed. Raised by the business-platform M3 integration review after an ops-core smoke test proved the behaviour; ops-core locks it with `SellableStatusEphemeralIdBehaviorTests`.

### Deprecated

- Operational Form v1 create/status/read operations, v1 form schemas, and `operational-form-type.yaml`; they remain usable during migration and have no approved removal date.

### Removed

- `BLOCKED` and `REJECTED` from `enums/ops/warehouse-receipt-status.yaml` and from the `GET /v1/warehouse-receipts` `status` filter. Neither token ever existed for warehouse receipts in the provider: a receipt against a non-RELEASED batch is refused at command time so no row is persisted in that state, and `REJECTED` carried an unresolved TODO admitting its semantics were never specified. Both belong to the packaging-intake vocabulary and were copied across by mistake. Safe to remove because no provider runtime emitted them and `GET /v1/warehouse-receipts` was unimplemented at removal time. Replaced by the canonical `CANCELLED` and `CORRECTED`. Owner decision `OD-C24-03` (2026-09-05).

### Fixed

- Corrected the v1 FRM-14 OpenAPI extension to the published v1 enum value `ACCOUNTING_MATERIAL_ISSUE`.
- Closed SKU lifecycle schema parity around the canonical registry: both Product Master and authenticated external public-SKU schemas now accept terminal `RETIRED`, reject internal-only `ACTIVE_BASELINE`, and are enforced by focused validation plus the X03B contract test in CI.

### Breaking Changes

- Operational Forms v2 replaces required v1 identity fields with canonical `form_key`. Consumers must opt into `/v2`; v1 is not silently changed or removed. See `compatibility/operational-form-v1-to-v2-migration.md`.
